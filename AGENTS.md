# Repository guidance for agents

This repository manages per-host system configuration with Ansible.

## Ownership and architecture

- Top-level `<hostname>.yml` playbooks own host composition and role inputs under `vars.confmgmt`.
- `roles/meta/tasks/main.yml` is the generic dispatcher: it includes one role for every `confmgmt` key, in mapping order. Keep host-specific wiring out of it.
- The order of keys under `confmgmt` is execution order and may express dependencies between roles. Do not reorder keys without considering that effect.
- Each `confmgmt` key must match a directory under `roles/`; roles own configuration behavior.
- Enable a role by adding its key under `vars.confmgmt` in the target playbook. Do not add it directly to the play's `roles:` list; the meta dispatcher owns role inclusion. An empty `role_name:` key enables a role with no inputs.
- `runner` is the normal execution entrypoint. `README.md` owns user-facing setup and usage documentation.

## Execution and dependencies

- `runner` creates and reuses `${HOME}/.cache/conf-mgmt/venv`, rebuilding it whenever the pinned `requirements.txt` changes. Use that environment for Ansible commands and module tests rather than assuming the system Python has the required packages.
- `requirements.in` is the dependency source and `requirements.txt` is generated by `pip-compile requirements.in`. Do not edit the generated file by hand.
- Ansible modules execute on the managed host. Keep role-local modules limited to the Python standard library and `ansible.module_utils` unless the role explicitly guarantees another target-side dependency.
- Make privilege transitions explicit with `become` and `become_user`; do not assume the controller user, SSH user, and target package owner are the same account.

## Role pattern

- For a new role, start with `roles/<role_name>/tasks/main.yml`:

  ```yaml
  - name: role_name
    tags: [role_name]
    block:
    - name: describe the change
      module_name:
  ```

- Read inputs from `confmgmt.<role_name>`. Add `defaults`, `handlers`, `files`, or `templates` only for a current need; do not scaffold them speculatively.
- Follow the existing short module-name and YAML style. Prefer idempotent modules over commands.
- When a command is necessary, prefer `command` with explicit arguments unless shell syntax is required. Set accurate `changed_when` and, when needed, `failed_when`.
- Give managed system files explicit owner, group, and mode. Use inline `copy.content` for short configuration; use files or templates for substantial or variable content.
- Notify handlers for reloads or restarts so they run only after a change.
- Guard platform-specific work with facts. Playbooks gather only the `min` subset, so gather any additional fact subset inside the role.
- Comment non-obvious platform constraints, ordering, safety assumptions, and rationale; do not restate obvious task mechanics.
- Inspect only the target playbook, the meta loader, and the role being changed unless the task requires broader work.

## Custom modules

- Prefer built-in or collection modules when they express the required behavior clearly and efficiently.
- A small purpose-built module is appropriate when existing modules require repeated external commands, parse human-readable output for state, or force substantial orchestration into the playbook.
- Keep a role-specific module under `roles/<role_name>/library/` and use a `confmgmt_`-prefixed module name.
- Keep policy conservative in reusable module defaults; let the role explicitly enable operations such as upgrading or cleanup.
- Use machine-readable command output or documented exit codes for state detection when available. Batch independent package or argument operations when the underlying tool supports it.
- Implement check mode without mutations and declare its support honestly as full, partial, or none. When prediction is unavailable, return an explicit result field and document the limitation.
- Preserve partial `changed` state when an earlier mutation succeeds before a later operation fails.
- Return stable candidate and per-operation change fields where useful, plus a concise final `msg` suitable for verbose Ansible output.
- Add focused unit coverage under `tests/` for input validation, no-op behavior, bulk mutations, check mode, and partial failures.
- Document module options and return values so `ansible-doc -M roles/<role_name>/library <module_name>` succeeds.

## Commit messages

- Create commits only when explicitly requested.
- Prefer a concise scope-first subject in the form `<scope>: <summary>` so the affected area is visible in short logs. This is a convention, not a strict schema.
- Use the narrowest useful scope: a role name for role work (`flatpak: add bulk management module`), a hostname for composition changes (`tomoyo: update kernel arguments`), or a specific repository area (`requirements.txt: refresh lock file`).
- Multiple scopes may be comma-separated when one cohesive change genuinely affects them together, as in `hagane, sabre: update shared packages`.
- Keep unrelated changes in separate commits instead of stretching the scope or summary to cover them.

## Safety and verification

- Keep repository guidance generic. Do not add user-specific absolute paths, credentials, host secrets, or private configuration to `AGENTS.md`.
- Treat `runner local` and `runner remote` as live system mutations: they may install packages, replace configuration, or restart services. Run them only when explicitly requested and use `-- --tags <role_name>` when a targeted run is sufficient.
- Run `./runner syntaxcheck <hostname>.yml` for every changed playbook. When changing only a role, syntax-check at least one playbook that enables it for each affected platform. This checks parsing, not whether deployment succeeds on the target host.
- Run focused tests for every changed custom module and the complete `${HOME}/.cache/conf-mgmt/venv/bin/python -m unittest discover -v tests` suite before handoff.
- For documentation-only changes, inspect the final text and run `git diff --check`.
- Treat `locals.yml` as ignored machine-local configuration: do not print or commit it.
